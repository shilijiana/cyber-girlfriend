## 1. 任务背景与目标

### 背景
「赛博女友」已完成 M0~M4 全部开发，M5-02~05 收尾、v0.1.0 发布。架构红线 5 要求**依赖最小化**（运行时 5-6 个纯 JS 依赖，零原生编译）。老板明确：**依赖审计（CC-02）非 Hermes 长处，由 Claude Code 执行，放 M5 最后做**——此时依赖清单稳定，审计结果有最终参考价值。

### 目标
对项目**两个 package.json（根 + client）**做依赖健康度与安全审计（**只诊断、不改动**），输出结构化报告，确认：依赖最小化达标、无已知安全漏洞、配置合理、密钥安全。

## 3. 具体实施步骤（分阶段）

### 阶段 A：环境准备（约 5 分钟）
1. `cd D:/其他资料/赛博女友`
2. 确认 npm 版本：`npm --version`
3. 记录基线：`npm ls --depth=0`（根）+ `cd client && npm ls --depth=0`

### 阶段 B：依赖清单分析（根 + client 分别做）
1. **最小化检查**（红线 5）：
   - 根 dependencies 应**仅** `express` + `ws`；client dependencies 应**仅** `react` + `react-dom`
   - `npm ls --depth=0` 是否有**已安装但未使用**的包（对照 import 语句核实）
   - devDependencies 是否合理（@types/typescript/vite/esbuild 等构建工具）
2. **版本健康**：是否有 deprecated（弃用）包、过旧版本、重复依赖

### 阶段 C：安全漏洞扫描
1. 根：`npm audit`（如 node_modules 完整则直接跑）
2. client：`cd client && npm audit`
3. 记录：漏洞数量、严重程度（critical/high/moderate/low）、受影响的包与版本、修复建议（`npm audit fix` 预览）

### 阶段 D：配置与密钥安全
1. **tsconfig 合理性**（根 + client）：
   - `strict` 是否开启？module/moduleResolution 是否正确？
   - include 范围是否合理（不含 cybergirlfriend 旧目录、node_modules）
2. **密钥安全**：
   - `.env.example` / `config/apikeys.example.json` 是否只含占位符（无真实 Key）
   - `config/apikeys.json` 是否被 .gitignore 忽略（`git check-ignore` 验证）
   - 代码中是否有硬编码密钥（grep `sk-` / `apiKey=` / `token=`）
3. **.gitignore 覆盖**：node_modules、.env、dist、素材目录是否全覆盖

### 阶段 E：撰写交付物
按第 4 节格式写报告 + 填写反馈文档 + DEVLOG 记录。

## 5. 注意事项与边界范围

### 边界（明确不做的）
- ❌ **不改动任何文件**（不 `npm install` / 不 `npm audit fix`，只诊断；修复由后续任务执行）
- ❌ 不审查 `cybergirlfriend/` 旧脚手架依赖（已归档）
- ❌ 不检查业务逻辑（那是 CC-01 代码审查的活）

### 注意
- 两个 package.json 都要审（根 + client），分别报告
- `npm audit` 若因网络失败，记录失败原因，改为基于 package-lock 的人工核对
- 区分"红线达标项"（如 express+ws 最小化 ✅）与"建议项"

# 单模块测试执行与整改文档（配套文档）

> **文档性质**：配套执行文档——用于**缺陷记录、整改跟踪、回归验证与结果同步**。与《单模块测试计划》配套使用。
> **配套关系**：测试计划定义"怎么测"；本文档定义"测出问题怎么办"。
> **版本**：v1.0 · 2026-08-10

---

## 1. 文档用途与使用对象

| 角色 | 用途 |
|------|------|
| 子任务 agent（WorkBuddy / Claude Code） | 执行测试时记录缺陷、执行整改、填写回归结果 |

| 老板 | 查看缺陷清单与整改进度（文档即状态） |

### 1.1 与主文档的接口约定
- 用例 ID、模块号、判定准则**全部沿用主文档**（术语一致）
- 测试完成后，本文档 §2 缺陷清单、§4 状态同步为**必填区**

## 2. 缺陷记录与整改跟踪

### 2.1 缺陷条目模板（每个 FAIL 用例一条）

```
┌─────────────────────────────────────────────────────────────┐
│ 缺陷ID:    DEF-<模块号>-<3位序号>    例: DEF-M-V-001          │
│ 关联用例:  <用例ID>                  例: M-V-TC-005            │
│ 严重程度:  [严重 / 一般 / 轻微]                               │
│ 状态:      [新建 / 整改中 / 已验证关闭 / 挂起]                 │
│ 发现日期:  YYYY-MM-DD                                        │
│                                                              │
│ ── 问题描述 ──                                               │
│ <现象：实际行为 vs 预期行为的差异，含关键输出/报错>              │
│                                                              │
│ ── 复现步骤 ──                                               │
│ 1. <具体操作/命令>                                            │
│ 2. <预期 vs 实际>                                             │
│                                                              │
│ ── 根因分析 ──                                               │
│ <定位到文件:行号 / 模块内部原因>                               │
│                                                              │
│ ── 整改方案 ──                                               │
│ <改哪个文件、怎么改、风险点>                                   │
│                                                              │
│ ── 整改记录 ──                                               │
│ 整改人: <agent> · 日期: <date> · 变更: <commit hash>          │
│                                                              │
│ ── 回归验证 ──                                               │
│ 回归命令: <重跑命令> · 结果: [PASS/FAIL] · 日期: <date>        │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 严重程度定义

| 级别 | 定义 | 处理时限 |
|------|------|----------|
| **严重** | 主功能不可用 / 数据丢失风险 / 安全漏洞 | 立即整改 |
| **一般** | 功能部分异常 / 边界场景错误 | 本批次整改 |
| **轻微** | 体验问题 / 代码规范 / 潜在隐患 | 可延后，记录在案 |

### 2.3 缺陷状态流转

```
新建 → 整改中 → 已验证关闭
  │        │
  └→ 挂起（无法复现/需外部依赖/老板决定暂缓）
```

| 状态 | 含义 | 进入条件 |
|------|------|----------|
| 新建 | 已记录待整改 | 测试发现 FAIL |
| 整改中 | 正在修复 | 已提交整改方案并开始修改 |
| 已验证关闭 | 整改完成且回归通过 | 回归测试 PASS |
| 挂起 | 暂不处理 | 无法复现 / 依赖缺失 / 老板拍板 |

## 3. 自动整改与回归流程

### 3.1 检测到异常后的自动整改流程（子任务执行）

```
测试 FAIL 检出
   ↓ ① 记录缺陷（§2.1 模板，状态=新建）
   ↓ ② 根因分析（读源码/契约，定位文件:行号）
   ↓ ③ 制定整改方案（§2.1 整改方案栏）
   ↓ ④ 修改代码（遵守红线：先改契约→再改代码）
   ↓ ⑤ 记录整改（整改人/日期/commit hash）
   ↓ ⑥ 回归测试（重跑原用例 + 同模块相关用例）
   ↓
PASS？→ 状态=已验证关闭 → 更新本文档
FAIL？→ 回到 ④ 继续整改（最多 3 次，超限上报）
```

### 3.2 整改代码规范（红线提醒）
- 先改 `docs/architecture/module-contracts.md`（若接口变更）→ 再改代码
- 不引入新依赖（依赖最小化红线）；不新增持久化
- 整改提交信息：`fix(<模块>): <问题简述>（DEF-<ID>）`

### 3.3 回归测试范围
| 整改范围 | 必跑回归 |
|----------|----------|
| 单函数修改 | 该用例 + 同文件其他用例 |
| 模块内多文件 | 该模块全部 L1/L2 用例 |
| 跨模块接口变更 | 相关模块用例 + `npx tsc --noEmit` |

### 3.4 回归验证模板
```
回归用例: <用例ID>（关联 DEF-<ID>）
回归命令: node --experimental-strip-types <测试文件>
回归结果: [PASS / FAIL]
回归日期: YYYY-MM-DD
备注: <额外验证，如 tsc 结果>
```

## 4. 测试结果同步与文档更新规范

### 4.1 文档更新时机（强制）
| 时机 | 必须更新内容 |
|------|--------------|
| 每条用例执行完 | 用例实际结果/判定 |
| 每个 FAIL 检出 | §2 缺陷清单新增条目（状态=新建） |
| 每次整改完成 | 缺陷条目补整改记录（§3.4 回归结果） |
| 模块测试收尾 | §4.2 状态汇总表 + §4.3 模块结论 |
| 全部模块测完 | §4.4 全局汇总 |

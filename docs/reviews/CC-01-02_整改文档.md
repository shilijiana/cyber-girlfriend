## 1. 问题整改明细（逐条记录）

> **填写规范**：每条问题按下列模板记录。**已整改**填处理过程与验证；**未整改**填原因与建议。

### 1.1 🔴 高严重度（H1~H9）

#### H1. orchestrator.ts:83-131 无请求级超时
- **原因分析**：chat() 直接 await brain 执行，未做总超时控制；Hermes 卡死时 HTTP 永久挂起
- **整改内容**：chat() 用 `Promise.race([run, timeoutResult])` 包总超时（60s），超时返回 `ok:false + 友好提示`（HTTP 200）；配套 M2 串行队列 + L8 单次 brain 超时 45s + L9 脱敏
- **处理过程**：`app/server/orchestrator.ts`——新增 `CHAT_TIMEOUT_MS = 60_000` / `BRAIN_TIMEOUT_MS = 45_000`；chat() 拆为并发控制层 + `doChat()` 内部实现；finally 清理超时 timer
- **验证结果**：根 tsc 零错误；orchestrator-degradation-test 通过；超时路径返回 HTTP 200 + ok:false（契约 §3.3 语义不变）
- **状态**：✅ 已整改

#### H2. loader.ts:104,116,125 `||` vs `??` 语义错误
- **原因分析**：falsy 值（空串/0）被 `||` 错误替换为默认值，如 baseUrl 显式置空无法禁用自定义端点
- **整改内容**：`config/loader.ts` `mergeWithEnv` 全部 `||` 改 `??`；`server.port` 按整改说明保留 `||`（NaN 兜底需要）
- **处理过程**：逐字段替换 + 注释说明语义；同步修正 M4（import.meta.url 推导根目录）、M5（os.homedir() 动态 personasDir）
- **验证结果**：根 tsc 零错误；空串配置保留原值，端口 NaN 仍回退 3000
- **状态**：✅ 已整改

#### H3. ws.ts:93-97 无连接数限制/认证/Origin 校验
- **原因分析**：WS 完全开放，可被资源耗尽攻击；无 Origin 校验存在跨站劫持风险
- **整改内容**：基础加固——`DEFAULT_MAX_CONNECTIONS = 10`（deps 可覆盖）+ Origin 白名单校验（仅放行 localhost/127.0.0.1 任意端口，无 Origin 的 Node 客户端放行）；完整认证机制按范围外约定另行设计
- **处理过程**：`app/server/ws.ts` connection 回调加两道检查（Origin 不合 → 1008 关闭；超限 → 1013 关闭）；新增 `maxConnections` 依赖注入；L10 同时补 `.catch()`
- **验证结果**：根 tsc 零错误；ws-test 全部通过（无 Origin 客户端不受影响）；超限/跨源场景以日志+关闭帧兜底
- **状态**：✅ 已整改（基础加固；认证属范围外）

#### H4. function-router.ts:199 handle() 未 try-catch runner.run()
- **原因分析**：违反"handle 不抛错"契约，runner 异常会导致上游 gateway 崩溃
- **整改内容**：`brain/function-router.ts` handle() 中 try-catch 包裹 `runner.run()`，异常走 `fail(callId, '大脑执行异常：…')`
- **处理过程**：局部 try-catch + 注释说明防御性兜底（契约 §3.3 错误语义）
- **验证结果**：根 tsc 零错误；function-calling-unit-test 全部通过
- **状态**：✅ 已整改

#### H5. hermes-runner.ts:71 输出上限合并计数
- **原因分析**：stdout+stderr 合计 1MB，大量 stdout 会挤占 stderr 空间，丢失关键错误信息
- **整改内容**：`brain/hermes-runner.ts` stdout / stderr 各自独立 1MB 上限，互不挤占
- **处理过程**：`appendLimited` 按流分别截断；同步修 M6（stderr 正则精确化 `/^(?:error:|traceback|unhandled exception)/im`）、M7（Windows taskkill 杀进程树）、L12（timeoutMs 下限 1s）、L13（串行队列 max 1）
- **验证结果**：根 tsc 零错误；qwen-fallback-test 15/15 通过（无 Hermes 真进程回归项）
- **状态**：✅ 已整改

#### H6. file-persona-provider.ts:46-52 路径注入风险
- **原因分析**：memoryFilePath 绝对路径直接拼入 LLM 指令，路径含换行/控制符可被利用做提示注入
- **整改内容**：`buildClosingInstruction` 新增 `sanitizePathForInstruction`（过滤 `\n\r\t`）；`resolveIdDir` 增加 `startsWith(personasDir)` 二次校验（防 `../` 穿越绕过 ID_PATTERN）
- **处理过程**：`persona/file-persona-provider.ts` 两处修改 + 注释；同步 M10（运行期异步 IO）、M11（JSON.parse 错误包装）、M12（缺省改注册表第一个 id）
- **验证结果**：根 tsc 零错误；路径含换行被过滤，越界路径抛"路径越界"错误
- **状态**：✅ 已整改

#### H7. hermes-persona-provider.ts 死代码含安全漏洞
- **原因分析**：零 import，已被 FilePersonaProvider 替代（ADR-008），残留含 id 注入 LLM 风险
- **整改内容**：`git rm persona/hermes-persona-provider.ts` 整文件删除
- **处理过程**：grep 确认全代码库零 import（仅文档提及）后删除；删除后 tsc 零错误确认无引用
- **验证结果**：`git status` 显示 deleted；根 tsc 零错误
- **状态**：✅ 已整改

#### H8. gateway.ts:122 JSON 以二进制帧发送
- **原因分析**：`browserWs.send(Buffer.from(...))` 发二进制帧（opcode 0x02），浏览器 onmessage 收到 Blob/ArrayBuffer 需额外转换
- **整改内容**：`voice-shell/gateway.ts` sendToBrowser 改 `browserWs.send(JSON.stringify(obj))`（文本帧 opcode 0x01）
- **处理过程**：一行修改 + 注释说明原因
- **验证结果**：根 tsc 零错误；gateway-unit-test 全部通过（浏览器侧收到 string）
- **状态**：✅ 已整改

#### H9. useVoice.ts:177-179 connect() 竞态
- **原因分析**：async 函数 + 闭包捕获 status，快速双击两次读到 idle 创建双重 mic/player/ws 资源，第一套泄漏
- **整改内容**：`client/src/hooks/useVoice.ts` 新增 `connectingRef` 互斥锁，try/finally 统一释放
- **处理过程**：connect 开头 `if (connectingRef.current) return; connectingRef.current = true;`，主体包 try/finally 复位；L20 同步改 WS URL 协议自适应（https → wss）
- **验证结果**：client tsc 零错误；use-chat/voice 相关测试通过
- **状态**：✅ 已整改

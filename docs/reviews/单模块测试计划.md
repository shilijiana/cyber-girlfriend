# 单模块测试计划（主文档）

> **文档性质**：主测试计划——子任务 agent（WorkBuddy / Claude Code 等）**直接阅读本文件即可自动执行**单模块测试，无需额外解释。
> **适用范围**：赛博女友项目（`D:/其他资料/赛博女友`）全部 7 大模块的单模块功能测试。
> **配套文档**：`docs/reviews/单模块测试执行与整改文档.md`（缺陷记录、整改、回归与结果同步）。
> **版本**：v1.0 · 2026-08-10

---

## 1. 测试概述

### 1.1 目的
对项目 7 大模块逐一执行功能测试，验证每个模块的**正常路径、边界条件、异常输入**三类场景，产出标准化测试报告，发现缺陷并驱动整改。

### 1.2 被测模块清单

| 模块号 | 模块名 | 目录 | 核心产出 | 依赖 |
|--------|--------|------|----------|------|
| M-A | app 应用壳 | `app/` | orchestrator/routes/ws/降级 | brain, persona |
| M-B | brain 大脑 | `brain/` | hermes-runner/function-router/降级 | - |
| M-P | persona 人设 | `persona/` | FilePersonaProvider | - |
| M-V | voice-shell 语音壳 | `voice-shell/` | qwen-audio-client/gateway/dispatcher | - |
| M-AV | avatar 数字人 | `avatar/` | clip-matcher/emotion-matcher | - |
| M-C | config 配置 | `config/` | loader/apikeys | - |
| M-CL | client 前端 | `client/src/` | components/hooks/voice | app(API) |

### 1.3 测试分级
| 级别 | 含义 | 执行条件 |
|------|------|----------|
| **L1 单元测试** | 纯函数/单类逻辑验证 | 无外部依赖，可随时执行 |
| **L2 集成测试** | 模块内多组件协作 | 无需真实 API（mock 注入） |
| **L3 端到端冒烟** | 真实链路（真实 Hermes/Qwen） | 需要 API Key，**消耗额度，谨慎执行** |

> ⚠️ **默认执行 L1+L2**；L3 仅在任务明确要求时执行（消耗 API 额度）。

## 2. 环境准备（第 0 步）

### 2.1 前置条件检查
执行以下命令逐项确认环境就绪，**全部通过才可开始测试**：

```bash
cd D:/其他资料/赛博女友

# ① Node 版本（需 >= 22，支持 --experimental-strip-types 直跑 TS）
node --version | grep -E "^v(2[2-9]|[3-9])" && echo "PASS: node>=22" || echo "FAIL: node 版本过低"

# ② 依赖已安装（根 + client）
ls node_modules/.package-lock.json >/dev/null 2>&1 && echo "PASS: 根依赖已装" || echo "WARN: 根依赖未装，运行 npm install"
ls client/node_modules/.package-lock.json >/dev/null 2>&1 && echo "PASS: client 依赖已装" || echo "WARN: client 依赖未装，运行 cd client && npm install"

# ③ 类型检查基线（记录基线错误数，区分"基线问题"与"本次新增"）
npx tsc --noEmit 2>&1 | tail -5

# ④ 后端可启动（L3 才需要）
curl -s --max-time 3 http://localhost:3000/api/health 2>/dev/null | grep -q '"status":"ok"' && echo "PASS: 后端运行中" || echo "INFO: 后端未启动（仅 L3 需要）"

# ⑤ 清理临时产物
rm -f .tmp-*.mjs .tmp-*.ts tests/_tmp_*.ts 2>/dev/null; echo "DONE: 临时产物已清理"
```

### 2.2 测试目录约定
| 用途 | 路径 | 规则 |
|------|------|------|
| 测试报告 | `docs/reviews/test-reports/` | 每次执行生成一份，命名见 §6.3 |
| 测试脚本 | 各模块目录内 `*-test.ts` / `*-unit-test.ts` | 随模块入库，不入 `docs/reviews/` |
| 临时产物 | `%TEMP%` 或项目内 `.tmp-*` | 用后即清，**禁止入库** |

## 3. 测试范围界定

### 3.1 范围界定流程
1. **读任务要求**：明确本次要测的模块（如"测试 voice-shell"→ 只测 M-V）
2. **读契约**：`docs/architecture/module-contracts.md` 对应模块章节（接口签名、语义）
3. **列测试文件**：目标模块目录下的全部 `*-test.ts`
4. **确认边界**：模块对外接口 = 测试边界；**不测**依赖模块的内部实现（mock 掉）

### 3.2 模块 ↔ 测试文件映射表

| 模块 | 测试文件（L1/L2） | 运行命令 |
|------|-------------------|----------|
| app | `app/server/ws-test.ts`、`app/server/orchestrator-degradation-test.ts` | `node --experimental-strip-types app/server/ws-test.ts` 等 |
| brain | `brain/qwen-fallback-test.ts` | `node --experimental-strip-types brain/qwen-fallback-test.ts` |
| voice-shell | `voice-shell/gateway-unit-test.ts`、`dispatcher-unit-test.ts`、`function-calling-unit-test.ts`、`vad-unit-test.ts`、`transcript-unit-test.ts` | 各文件对应 `node --experimental-strip-types <file>` |
| avatar | `avatar/emotion-matcher-unit-test.ts` | `node --experimental-strip-types avatar/emotion-matcher-unit-test.ts` |
| client | `client/package.json` scripts（test:avatar/test:chat/test:voice 等） | `cd client && npm run test:avatar` 等 |
| persona | （暂无测试文件） | 需编写：见 §3.3 |
| config | （暂无测试文件） | 需编写：见 §3.3 |

### 3.3 无测试文件的模块（persona / config）
执行者需**先补最小测试脚本**再测：
- `persona/file-persona-provider-test.ts`：验证 readFile 加载、路径安全、缺失文件兜底
- `config/loader-test.ts`：验证文件优先/环境变量兜底/Key 读取

## 4. 测试用例设计规范

### 4.1 标准用例模板（每个功能至少 3 类用例）

```
┌─────────────────────────────────────────────────────────────┐
│ 用例 ID:   <模块号>-TC-<序号>    例: M-V-TC-001              │
│ 用例名称:  <一句话描述>           例: sendAudio 正常上行       │
│ 用例类型:  [正常路径 / 边界条件 / 异常输入]                    │
│ 前置条件:  <需要准备的环境/mock>                              │
│ 输入:      <具体输入值/参数>                                  │
│ 执行步骤:  1. ... 2. ... 3. ...（可执行命令）                 │
│ 预期结果:  <可断言的输出/状态/返回值>                          │
│ 实际结果:  （执行后填写）                                     │
│ 判定:      [PASS / FAIL / BLOCKED]                           │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 三类用例设计要点
| 类型 | 覆盖点 | 示例 |
|------|--------|------|
| **正常路径** | 主流程、happy path、标准输入 | 发消息→收到回复；连接→会话建立 |
| **边界条件** | 空值、最大值、极限时长、并发 | 空字符串 instruction；timeoutMs=0/负数/超上限；重复调用 |
| **异常输入** | 非法参数、缺失字段、错误类型、外部故障 | JSON 解析失败；未知工具名；provider 连接失败；WS 断开 |

### 4.3 用例编号规则
`<模块号>-TC-<3位序号>`，如 `M-V-TC-001`。模块号见 §1.2。

## 5. 执行步骤（分阶段）

### 阶段 0：环境准备
执行 §2 全部检查命令，确认 PASS。

### 阶段 1：目标模块静态核查
```bash
# 列出目标模块文件与测试文件
ls -la <模块目录>/            # 例: ls -la voice-shell/
ls -la <模块目录>/*-test.ts   # 确认测试文件存在
```

### 阶段 2：编写/补全测试用例
- 按 §4 模板为目标模块的每个功能设计用例（**先设计后执行**）
- 若模块无测试文件（persona/config），先按 §3.3 补最小脚本

### 阶段 3：执行测试（逐用例）
```bash
# 每条用例执行一次：
node --experimental-strip-types <测试文件>   # L1/L2 通用
# 或 client 模块：
cd client && npm run test:<子项>
# 记录：输出、退出码、耗时
echo "EXIT:$?"
```

### 阶段 4：结果记录
- 每条用例：在用例模板中填**实际结果 + 判定**
- FAIL 的用例：立即记录到配套整改文档（§6 缺陷记录）

### 阶段 5：汇总判定
- 统计 PASS/FAIL/BLOCKED 数量
- 生成测试报告（§6 格式），更新配套文档结论

## 6. 判定准则与报告规范

### 6.1 测试通过/失败判定

| 判定 | 条件 |
|------|------|
| **PASS** | 实际结果与预期完全一致，无未捕获异常，退出码 0 |
| **FAIL** | 断言失败 / 抛出未预期异常 / 输出与预期不符 / 退出码非 0 |
| **BLOCKED** | 前置条件不满足（如依赖未装、API Key 缺失），无法执行 |

**模块级结论**：
- **通过**：该模块全部用例 PASS，且无 FAIL 残留
- **不通过**：存在 ≥1 个 FAIL（必须进入整改流程）
- **部分通过**：有 BLOCKED 或未覆盖项（报告中说明原因）

### 6.2 测试报告输出格式

```markdown
# 单模块测试报告 - <模块名>
> 测试日期: YYYY-MM-DD · 执行者: <agent 名> · 测试级别: L1/L2(/L3)

## 摘要
| 指标 | 值 |
|------|-----|
| 用例总数 | N |
| PASS | N |
| FAIL | N |
| BLOCKED | N |
| 模块结论 | 通过 / 不通过 / 部分通过 |

## 用例明细
| 用例ID | 名称 | 类型 | 判定 | 备注 |
|--------|------|------|------|------|
| M-X-TC-001 | ... | 正常路径 | PASS | |
| ... | ... | ... | ... | |

## 环境信息
- Node: <版本>
- 基线 tsc: <错误数>
- 依赖: <已装/未装>
```

### 6.3 报告存储路径
```
docs/reviews/test-reports/<模块号>-<YYYYMMDD>-<执行者>.md
例: docs/reviews/test-reports/M-V-20260810-workbuddy.md
```

## 7. 测试执行清单（给子任务逐条执行）

> 子任务按以下编号顺序逐条执行，每完成一条打 ✓，全部完成即模块测试结束。

```
[ ] 1. 运行 §2 环境准备全部命令，记录 PASS/FAIL
[ ] 2. 确认目标模块与测试文件映射（§3.2），锁定测试边界
[ ] 3. 若模块无测试文件（persona/config），按 §3.3 编写最小测试脚本
[ ] 4. 按 §4 模板设计用例（每个功能：正常/边界/异常 ≥3 条），写入执行记录
[ ] 5. 逐条执行用例，运行对应测试命令，记录实际结果与退出码
[ ] 6. 所有 FAIL 用例：按配套文档 §2 记录缺陷（问题/复现/根因/整改方案）
[ ] 7. 生成测试报告到 docs/reviews/test-reports/<模块号>-<日期>-<执行者>.md
[ ] 8. 更新配套文档 §4 结论与状态同步
[ ] 9. 清理临时产物（.tmp-*、tests/_tmp_*）
[ ] 10. 若修改了代码/测试文件，提交 git（message 注明模块与测试）
```

## 8. 注意事项与红线

- ✅ **默认只跑 L1+L2**；L3（真实 API）仅在任务明确授权时执行（消耗额度）
- ✅ 测试脚本若需修改，遵守项目红线（无数据库/无持久化；依赖最小化）
- ✅ 契约变更先改 `module-contracts.md` 再改代码
- ⚠️ 不修改被测业务代码来"让测试通过"；FAIL 必须走整改流程
- ⚠️ 测试报告和整改文档是**唯一真相源**，执行完成后必须同步

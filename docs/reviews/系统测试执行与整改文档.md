# 系统测试执行与整改文档（配套文档）

> **文档性质**：配套执行文档——用于**系统测试（SYS）的缺陷记录、整改跟踪、回归验证与结果同步**。与《系统测试计划》配套使用。
> **配套关系**：系统测试计划定义"测什么场景、怎么测"；本文档定义"测出问题怎么办"。
> **关联文档**：《单模块测试执行与整改文档》（单模块缺陷记录，本文档专注系统级缺陷）。
> **版本**：v1.0 · 2026-08-10

---

## 1. 文档用途与使用对象

| 角色 | 用途 |
|------|------|
| 子任务 agent（WorkBuddy / Claude Code） | 执行系统测试时记录系统级缺陷、执行整改、填写回归结果 |
| 架构负责人（小呆） | 跟踪系统缺陷状态、核对跨模块整改、汇总系统结论 |
| 老板 | 查看系统缺陷清单与整改进度 |

### 1.1 与主文档的接口约定
- **场景号/用例 ID/判定准则**沿用《系统测试计划》（术语一致）：场景 `SYS-XX`、用例 `SYS-XX-TC-XXX`
- 缺陷 ID 前缀：**`DEF-SYS-`**（区分单模块的 `DEF-<模块>-`）
- 单模块缺陷 → 记录在《单模块测试执行与整改文档》；**系统级/跨模块缺陷 → 记录在本文档**

### 1.2 与单模块整改文档的分工

| 缺陷类型 | 记录位置 | 示例 |
|----------|----------|------|
| 单模块内部缺陷 | 单模块整改文档 §5 | 某函数边界错误 |
| **系统级/跨模块缺陷** | **本文档 §5** | 前端→后端→Hermes 链路不通；WS 音频格式不匹配；降级不生效 |

> 判断原则：缺陷能否在**单个模块内复现并修复**？能→单模块文档；不能（涉及多模块协作/链路）→本文档。

## 2. 缺陷记录与整改跟踪

### 2.1 缺陷条目模板（每个 FAIL 场景/用例一条）

```
┌─────────────────────────────────────────────────────────────┐
│ 缺陷ID:    DEF-SYS-<3位序号>       例: DEF-SYS-001            │
│ 关联场景:  <SYS-XX>                例: SYS-05                 │
│ 关联用例:  <SYS-XX-TC-XXX>         例: SYS-05-TC-002           │
│ 严重程度:  [严重 / 一般 / 轻微]                                │
│ 状态:      [新建 / 整改中 / 已验证关闭 / 挂起]                  │
│ 发现日期:  YYYY-MM-DD                                        │
│                                                              │
│ ── 问题描述 ──                                               │
│ <现象：实际行为 vs 预期，含关键输出/报错>                       │
│                                                              │
│ ── 复现步骤 ──                                               │
│ 1. <启动命令/请求命令>                                        │
│ 2. <预期 vs 实际>                                             │
│                                                              │
│ ── 跨模块定位 ──                                              │
│ 涉及模块: <如 client → app → brain>                           │
│ 定位文件: <文件:行号>（根因所在模块）                          │
│                                                              │
│ ── 根因分析 ──                                               │
│ <链路哪一环出错/契约是否违背>                                  │
│                                                              │
│ ── 整改方案 ──                                               │
│ <改哪些模块、怎么改、是否涉及契约变更>                         │
│                                                              │
│ ── 整改记录 ──                                               │
│ 整改人: <agent> · 日期: <date> · 变更: <commit hash>          │
│                                                              │
│ ── 回归验证 ──                                               │
│ 回归命令: <重跑场景命令> · 结果: [PASS/FAIL] · 日期: <date>    │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 严重程度定义（与单模块一致）

| 级别 | 定义 | 处理时限 |
|------|------|----------|
| **严重** | 主链路不可用 / 数据丢失风险 / 安全漏洞 | 立即整改 |
| **一般** | 某场景功能异常 / 边界错误 | 本批次整改 |
| **轻微** | 体验问题 / 性能基线 / 潜在隐患 | 可延后，记录在案 |

> ⚠️ **性能问题特殊处理**：M5-01 已知性能瓶颈（快问快答 20-39s，ACP 常驻待验证）记为"性能基线"（轻微），不按严重处理。

### 2.3 缺陷状态流转（与单模块一致）

```
新建 → 整改中 → 已验证关闭
  │        │
  └→ 挂起（无法复现/需外部依赖/老板决定暂缓）
```

## 3. 自动整改与回归流程

### 3.1 系统级缺陷自动整改流程（子任务执行）

```
系统测试 FAIL 检出
   ↓ ① 记录缺陷（§2.1 模板，状态=新建，DEF-SYS-*）
   ↓ ② 跨模块定位（链路哪一环出错，区分"上游/下游/中间层"）
   ↓ ③ 契约核对（先查 module-contracts.md 对应链路契约是否违背）
   ↓ ④ 制定整改方案（涉及模块 + 是否契约变更）
   ↓ ⑤ 修改代码（红线：先改契约→再改代码）
   ↓ ⑥ 记录整改（整改人/日期/commit hash）
   ↓ ⑦ 回归：重跑该场景全部用例 + 相邻场景
   ↓
PASS？→ 状态=已验证关闭 → 更新本文档
FAIL？→ 回到 ⑤ 继续整改（最多 3 次，超限上报老板）
```

### 3.2 整改代码规范（红线提醒）
- **跨模块变更必须先改 `module-contracts.md`**（接口签名/语义）→ 再改代码
- 不引入新依赖（依赖最小化）；不新增持久化
- 提交信息：`fix(<模块>): <问题简述>（DEF-SYS-<ID>）`

### 3.3 回归测试范围

| 整改范围 | 必跑回归 |
|----------|----------|
| 单模块内修复 | 该场景用例 + 该模块单模块测试 |
| 跨模块接口变更 | 涉及场景全部用例 + 契约相关模块单测 + `npx tsc --noEmit` |
| 链路级改动 | 全场景 SYS-01~12 重跑 + 前端 `npm run build` |

### 3.4 回归验证模板

```
回归场景: SYS-XX（关联 DEF-SYS-<ID>）
回归命令: <重跑命令，如 curl / node 脚本>
回归结果: [PASS / FAIL]
回归日期: YYYY-MM-DD
额外验证: tsc / vite build / 相邻场景
```

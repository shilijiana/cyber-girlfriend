## 1. 三文档体系

| 文档 | 定位 | 回答的问题 | 谁来读 |
|------|------|-----------|--------|
| **BLUEPRINT.md** | 项目蓝图 | 项目是什么？架构长啥样？红线在哪？ | 所有人（第一个读的文件） |
| **TASKS.md** | 任务看板 | 该干什么？做到哪了？依赖谁？ | 开发者 / 架构负责人 |

**配套文档（不在三文档之内，但被引用）：**

| 文档 | 用途 |
|------|------|
| `docs/architecture/overall-architecture.md` | 架构全貌（深入版蓝图） |
| `docs/architecture/module-contracts.md` | 模块接口契约（开发时必查） |

| `PROJECT_MEMORY.md` | 项目记忆（历史决策与选型） |

## 2. 工作流程

### 2.1 接到新任务时

```
老板下达任务
      │
      ▼
① 读 BLUEPRINT.md → 理解项目全貌，定位你的模块
      │
      ▼
② 读 module-contracts.md → 找到你模块的接口定义
      │
      ▼
③ 读 TASKS.md → 找到你的任务 ID、验收标准、依赖项
      │
      ▼
④ 检查依赖是否已完成 → 没完成则标记 🚫 BLOCKED
      │
      ▼
⑤ 在 TASKS.md 把任务状态改为 🔄 IN PROGRESS
      │
      ▼
⑥ 在 DEVLOG.md 开一条当日记录
      │
      ▼
⑦ 开始写代码
```

### 2.2 开发过程中

```
写代码
      │
      ├── 遇到架构问题 → 查 overall-architecture.md / ADR
      ├── 遇到接口问题 → 查 module-contracts.md
      ├── 需要改接口 → 先改 module-contracts.md 再改代码（契约优先）
      ├── 遇到阻塞 → TASKS.md 标记 🚫 BLOCKED + DEVLOG.md 记录原因
      └── 做了重要决策 → DEVLOG.md 记录
```

### 2.3 完成任务时

```
代码写完
      │
      ▼
① 对照 TASKS.md 验收标准自检
      │
      ▼
② TASKS.md 把任务状态改为 ✅ DONE
      │
      ▼
③ DEVLOG.md 记录：做了什么、遇到什么问题、怎么解决的
      │
      ▼
④ 如果新增/修改了接口 → 更新 module-contracts.md
      │
      ▼
⑤ 如果有重大架构变化 → 新增 ADR 条目
      │
      ▼
⑥ 通知架构负责人（小呆）做汇总检查
```

## 3. 文档维护规则

### 3.1 谁维护什么

| 文档 | 维护者 | 更新时机 |
|------|--------|----------|
| BLUEPRINT.md | 架构负责人 | 架构变更、新增模块、红线变化时 |
| TASKS.md | 任务执行者 + 架构负责人 | 接任务、状态变化、新增任务时 |
| DEVLOG.md | 任务执行者 | 每次开发 session 结束时 |
| module-contracts.md | 接口变更者 | 接口新增/修改时（**先改契约再写代码**） |
| ADR | 决策提出者 | 重大架构决策拍板时 |
| 模块 README.md | 模块开发者 | 模块功能变化时 |

### 3.2 更新频率

- **TASKS.md**：实时——状态一变就改
- **DEVLOG.md**：每次开发 session 结束时追加一条
- **BLUEPRINT.md**：架构变更时（不频繁）
- **module-contracts.md**：接口变更时（先于代码）
- **ADR**：重大决策时（不频繁）

### 3.3 格式规范

- 所有文档用 Markdown
- 中文为主，技术术语保留英文原词
- 表格优先于长段落
- 代码示例用 TS / JSON
- 日期格式：`YYYY-MM-DD`
- 版本标记：文档标题下方写 `版本 vX.X` + 变更说明

## 4. 任务管理规则

### 4.1 任务 ID 分配

| 模块 | 前缀 | 示例 |
|------|------|------|
| voice-shell | VS | VS-01 |
| brain | BR | BR-01 |
| persona | PS | PS-01 |
| avatar | AV | AV-01 |
| app | AP | AP-01 |
| client | CL | CL-01 |
| docs | DC | DC-01 |
| 里程碑级 | M{X} | M5-01 |

### 4.2 任务状态流转

```
📋 TODO → 🔄 IN PROGRESS → ✅ DONE
                │
                ├──→ 🚫 BLOCKED → 🔄 IN PROGRESS（解除阻塞后）
                │
                └──→ ⏸ PAUSED → 🔄 IN PROGRESS（恢复后）
```

### 4.3 新增任务

任何人发现需要做但 TASKS.md 里没有的事：
1. 在对应里程碑下新增一行，分配下一个可用 ID
2. 填写：任务描述、优先级、依赖、验收标准
3. 在 DEVLOG.md 记录"新增任务 XXX"

### 4.4 优先级调整

- P0 阻塞其他模块 → 必须先做
- P1 当前里程碑核心 → 优先做
- P2 增强 → 有空做
- P3 后续 → 以后做

优先级调整在 DEVLOG.md 记录原因。

### 4.5 派活模板（老板 / 架构负责人用）

派子任务时，把下面的模板发给子代理，它就能自主执行完整闭环。

**模板 A · 一句话版（推荐，子代理自举）**

> 读 `docs/WORKFLOW.md`，按里面的流程执行 `docs/TASKS.md` 中的 **{任务ID}** 任务。

子代理会顺着 WORKFLOW → BLUEPRINT → module-contracts → TASKS → DEVLOG 自举，完成"接任务 → 干活 → 记日志 → 更看板"。

**模板 B · 完整版（减少阅读轮次，加速定位）**

> 你是 **{模块名}** 模块开发者。先读 `docs/BLUEPRINT.md` 了解项目全貌，再读 `docs/architecture/module-contracts.md` 查 **{接口}** 接口定义，然后执行 `docs/TASKS.md` 中的 **{任务ID}**（{任务简述}）。完成后更新 TASKS 状态并在 `docs/DEVLOG.md` 记录。

**占位符填写示例**（以 AV-01 为例）：

| 占位符 | 示例值 |
|--------|--------|
| {模块名} | avatar 模块 |
| {接口} | ClipMatcher |
| {任务ID} | AV-01 |
| {任务简述} | clip-matcher 迁移与适配 |

**派活注意**：
- 模板 A 是底线——子代理只要读到 WORKFLOW.md 就能自举，不需要额外解释
- 模板 B 用于让子代理少读几轮文档、更快开工
- 派活后，子代理第一步应把任务标为 🔄 IN PROGRESS（§2.1 流程第⑤步）

## 5. 架构变更流程

当需要改变架构（新增模块、修改职责边界、更换技术选型等）：

```
发现问题/新需求
      │
      ▼
① 在 DEVLOG.md 记录问题描述
      │
      ▼
② 出方案（写到 DEVLOG.md 或独立文档）
      │
      ▼
③ 提交给老板评审
      │
      ▼
④ 老板拍板后：
   - 新增 ADR 条目（docs/adr/README.md）
   - 更新 overall-architecture.md
   - 更新 module-contracts.md（如涉及接口）
   - 更新 BLUEPRINT.md（如涉及模块/红线）
   - 更新 TASKS.md（如涉及任务调整）
   - 在 DEVLOG.md 记录最终决策
      │
      ▼
⑤ 开始执行
```

**红线**：任何架构变更必须先经过老板确认，不得擅自修改架构设计。

## 6. 沟通规则

- **老板 → 架构负责人**：下达任务、拍板决策、调整方向
- **架构负责人 → 模块开发者**：分配任务、检查进度、做汇总
- **模块开发者 → 架构负责人**：报告进度、反馈阻塞、提议变更
- **模块开发者之间**：通过 module-contracts.md 对齐接口，不直接耦合

## 7. 检查清单

### 每次开发 session 开始前
- [ ] 读 TASKS.md 确认当前任务与状态
- [ ] 读 DEVLOG.md 最新条目了解上次进度
- [ ] 检查依赖任务是否已完成

### 每次开发 session 结束前
- [ ] 更新 TASKS.md 任务状态
- [ ] 在 DEVLOG.md 追加一条记录
- [ ] 如有接口变更，更新 module-contracts.md
- [ ] 如有阻塞，在 TASKS.md 标记并说明原因

### 每个里程碑结束时
- [ ] 所有任务状态为 ✅ 或明确标记 🚫/⏸
- [ ] DEVLOG.md 有完整的里程碑总结
- [ ] BLUEPRINT.md 里程碑状态更新
- [ ] ADR 如有新决策已记录
- [ ] 通知老板做里程碑评审

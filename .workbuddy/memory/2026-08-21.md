## 修复：Edge 不显示视频，只显示"待机中"（老板反馈，WorkBuddy 预览正常）

- **根因**：数字人素材编码是 **MPEG-4 Visual (mp4v)**（老式 DivX/Xvid）——**浏览器（Edge/Chrome/Firefox）不支持 mp4v**，video 加载 onError → 降级 fallback"待机中"；WorkBuddy 内置 Chromium 带完整 ffmpeg 解码器所以能放。
- **修复**：用 imageio-ffmpeg 自带二进制 `ffmpeg-win-x86_64-v7.1.exe`（`~/.workbuddy/binaries/python/envs/default/Lib/site-packages/imageio_ffmpeg/binaries/`）把 6 个素材转码为 **H.264 + AAC**：`-c:v libx264 -preset medium -crf 23 -pix_fmt yuv420p -c:a aac -b:a 128k -movflags +faststart`；原文件备份到 `assets/avatars/clips/_originals_mp4v/`。转码后体积 2.7MB→0.75MB（-72%）。
- **验证**：扫描 ftyp/编码标识确认 avc1（H.264）；curl 200 OK（791KB）。Edge 可正常播放。
- **启示（重要）**：HY-Image VideoGen 产出的 mp4 是 mp4v 编码，**每次新生成素材都必须转码 H.264** 浏览器才能播。**可复用转码命令**（ffmpeg 在 `C:/Users/chipsine/.workbuddy/binaries/python/envs/default/Lib/site-packages/imageio_ffmpeg/binaries/ffmpeg-win-x86_64-v7.1.exe`）：
  ```bash
  ffmpeg -y -i in.mp4 -c:v libx264 -preset medium -crf 23 -pix_fmt yuv420p -c:a aac -b:a 128k -movflags +faststart out.mp4
  ```
  检查编码：`ffmpeg -i in.mp4`（看 Video: mp4v / h264）或 node 扫文件头编码标识（avc1=H.264 / mp4v=MPEG-4 Visual）。

## 修复：看不到回复的文字（老板反馈"能看到我说的文字，看不到回复的文字"）

- **排查链路**：后端日志（VAD 正常、Qwen 会话正常）→ `/api/chat` 文字链路正常（curl 实测返回小呆回复）→ Qwen 官方文档确认 `response.audio_transcript.delta` 是该模型标准事件 → **锁定前端 bug**。
- **根因（React StrictMode 双调用 updater）**：`main.tsx` 开了 `<React.StrictMode>`，dev 下 React 会把 `setState` updater **调用两次**检测副作用。旧代码在 `onSubtitle` 的 updater **内部**创建消息 id 并设置 `liveIdRef`（副作用）：第一次调用创建消息返回 `[msg]`，第二次调用时 liveIdRef 已有值 → 走"更新已有消息"分支 → 数组里没有 → 返回 `[]` → **live 消息被吞**，且 liveIdRef 被污染，之后所有副文本永远进更新分支找不到消息 → 回复文字永不显示。用户转写（纯追加无副作用）能显示，症状吻合。
- **修复（client/src/App.tsx）**：消息 id 创建移到 updater **外**（onSubtitle 用 `liveIdRef.current ?? createMessageId()`，onUserTranscript 先 `createMessageId` 再 commitVoice）；updater 内做幂等判断（`prev.some(m => m.id === id)`：存在则更新、不存在则创建、同 id 跳过），StrictMode 双调用结果一致。
- **验证**：typecheck 零错误 + build 通过；HMR 生效。真实语音副文本显示待老板刷新测试确认。
- **经验**：React StrictMode 下 `setState` updater 必须**纯函数**——任何在 updater 内做的副作用（ref 赋值、id 生成、外部状态写入）都会因双调用产生 bug；id 生成一律提到 updater 外 + updater 内幂等。

## 修复：对话顺序错乱（老板截图钉死：消息 1/6 位置提前）

- **症状**：用户消息 2 "小呆有休息没有？" 后是小呆回复 1 "老板，小呆一直在线..."（OK），但**小呆回复 1 排在用户 2 前面**；小呆回复 6 "嘿嘿老板夸我啦" 排在用户 7 "好的小呆..." 前面。预期：2→1→3→4→5→7→6（按对话轮次），实际显示 1→2→3→4→5→6→7。
- **根因**：Qwen Realtime 的 `conversation.item.input_audio_transcription.completed`（user transcript final）与 `response.audio_transcript.delta`（asst 副文本流式）**到达顺序不确定**（race condition）——纯用 `Date.now()` 作 ts 完全依赖到达顺序，race 时小呆回复偶尔排到用户消息前面。文字聊天链路（useChat）无此问题，因为发→pending→回复有序。
- **修复（App.tsx）**：
  - 新增 `seqRef`（单调递增逻辑时间戳：`Math.max(seqRef+1, Date.now())`）保证整体有序；
  - 新增 `lastUserTsRef`（最近 user 消息的 ts，作为本轮锚点）保证 asst.ts ≥ user.ts + 1；
  - onUserTranscript 创建 user 时设 `lastUserTsRef.current = ts`；onSubtitle 创建新 asst 时 `ts = Math.max(nextSeqTs(), lastUserTsRef+1)`。
  - 现有消息追加不更新 ts（保持累积位置）。
- **验证**：typecheck + build 通过；HMR 生效。
- **经验**：合并多源异步流（如语音 ASR + 回复生成并发）时，不能用 Date.now() 作时序锚点，必须用**单调 seq + 语义锚点**（user 转写作为"轮次锚"，asst 排在锚后）。同一逻辑适用于任何 S2S/全双工对话场景。

## 修复：VAD speech_started 锚定轮次起点（已连接态顺序错乱）

- **症状（老板对比截图）**：speaking 状态时 asst live 在上"对"（醒目）；connected 状态时 asst 定稿排在上"错"——期望 connected 时按时间顺序：user 在前、asst 在后。

- **修复（App.tsx）**：改用 VAD `speech_started` 作为轮次起点锚点（远早于 Qwen 处理后任何事件，本地 VAD 检测）：
  - 新增 `placeholderIdRef` + 复用 `lastUserTsRef`
  - onVadState(true) → 立即创建 user 占位消息（text=''，ts=seq+1），记锚点

- **经验**：Qwen Realtime / S2S 多源异步事件流下，**真正的"用户开始说话"事件是本地 VAD speech_started**（< 200ms），Qwen 转写 final 是 1-2 秒后的派生事件；用 VAD 锚点比用 Qwen 转写锚点早 1-2 个数量级，无 race。
